# Rollback Checklist：升级决策与回滚验收

配套 SKILL.md「升级决策检查单」的执行细则。走读 2026-09-02，机制事实以 ESP-IDF 基线 §5 为准。

## 1. 升级前决策单（逐项打勾，缺一不升）

| # | 检查项 | 通过标准 | 不通过的替代 |
|---|---|---|---|
| 1 | 版本比较 | 目标版本 > 当前版本（语义化比较，非字符串字典序） | 拒绝降级请求；降级需求评估防回滚/`esp32-secureboot` |
| 2 | 分区预算 | 读 target：新镜像大小 ≤ OTA 槽 size | 重排分区表（Offset 留空自动排布），再读一遍 |
| 3 | 电量/窗口 | 电量 ≥ 阈值；处于业务空闲窗口 | 推迟到充电/空闲期；UPS/常供电设备免检电量 |
| 4 | 网络质量 | 升级链路稳定；失败退避策略已实现 | 延后升级；禁止"失败立即重试"风暴 |
| 5 | 通道安全 | HTTPS + 服务器证书校验开启 | 不允许明文 HTTP 拉镜像（安全立场） |
| 6 | 回滚预案 | ROLLBACK_ENABLE + 自检确认代码已合入并演练 | 先补确认逻辑再升级 |
| 7 | 验收通道 | 灰度/测试设备先行 | 直接全量推送 = 高风险操作，需用户显式确认 |

## 2. 自检确认设计（反陷阱落点）

新镜像启动后、调用 `esp_ota_mark_app_valid_cancel_rollback()` 前，至少自检：

1. 关键外设初始化成功（否则 `esp_ota_mark_app_invalid_rollback_and_reboot()`）。
2. 网络能建立（配网凭据未被新版本破坏 → 问题则连带排查 `esp32-wifi-provision`）。
3. 业务心跳/关键任务运行若干个周期。
4. **确认调用必须在有限时间内执行**——自检卡死 = 永不确认 = 重启回滚（这是机制，不是 bug）。

## 3. 回滚验收（真机，Pending HIL until executed）

1. **正向**：升级 → 新版本上报 → otadata 显示新槽 VALID。
2. **显式失败回滚**：测试镜像自检必失败 → 设备回到旧版 → 旧版可再次发起升级。
3. **未确认回滚**：注释掉确认调用 → 重启后回旧版（验证对 ROLLBACK 语义的理解）。
4. **升级中断**：下载/写入中途断电 → 重启后设备运行原版本，可重新升级。
5. 每项记录：镜像版本、otadata 状态、串口日志——无记录不得声称"回滚已验证"。
6. 无真机：全部标 `Pending HIL`，移交 `fw-hil-testing` 执行并出证据。

## 4. 排障速查：升级后重启进旧版

| 线索 | 结论 | 动作 |
|---|---|---|
| 确认调用从未执行（任务卡死/崩溃在前） | PENDING_VERIFY 未确认 → 机制性回滚 | `esp32-debug` 看 coredump/复位原因；修自检路径 |
| 忘写确认调用 | 同上，最常见 | 补 `esp_ota_mark_app_valid_cancel_rollback()` |
| `esp_ota_end` 失败仍 set_boot_partition | 校验失败不该切槽 | end 失败必须终止升级流程 |
| 新镜像连不上网导致"看起来回滚" | 可能是凭据/服务端问题 | 先读启动日志确认实际运行的版本再下结论 |

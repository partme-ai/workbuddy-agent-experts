# Crash Triage：复位原因分类与随机重启决策树

走读 2026-09-02。机制事实（coredump 自动保存、idf.py 命令）出自 ESP-IDF 基线 §10，高置信；具体日志关键词/横幅样式未逐条抓取——判定以**实际 monitor 输出为准**，不凭记忆给固定字符串。

## 1. 三类复位原因定位表

| 类别 | 机制 | 证据来源（按顺序取） | 下一步 |
|---|---|---|---|
| panic（软件崩溃） | 异常触发，coredump 自动保存（基线高置信） | monitor 现场的 panic 输出与回溯；coredump 分区内容 | Workflow A：coredump-info/coredump-debug 符号化 |
| 看门狗复位 | 任务长阻塞/关中断过久等触发复位 | 启动日志的复位原因行 + 复现实验；无 panic 回溯却有复位记录 | 检查长阻塞代码、关中断时长；并发设计 → `esp32-freertos` |
| 掉电/供电类 | 电压跌落或复位信号异常导致重启 | 软件日志常无崩溃证据，重启时机与负载/外设动作相关 | 收集相关性证据 → **hand-off `fw-hil-testing`** 实测定论 |

分类纪律：**一次只下一层结论**。先回答"是哪一类"，再谈根因；软件日志干净 + 与负载强相关 = 硬件嫌疑，不等于硬件定论。

## 2. 随机重启排查决策树

```text
设备随机重启
├── 1. 串口还连得上吗？
│   ├── 是 → idf.py monitor 长时间蹲守，抓到重启瞬间
│   │        ├── 重启前有 panic 输出与回溯 → panic 类（Workflow A）
│   │        ├── 重启前无崩溃证据，boot 日志显示复位原因 → 按 §1 表归类
│   │        └── 什么都没有、说断就断 → 掉电/供电嫌疑（步骤 3）
│   └── 否 → 先解决观察通道（串口永不可少）；确认 coredump 配置在不在
├── 2. coredump 配置了吗（flash/UART）？
│   ├── 是 → 提取历史现场：idf.py coredump-info（概览）→ coredump-debug（符号化）
│   └── 否 → 证据已被覆盖：先补配置（coredump 分区 + 目的地），再造复现条件
├── 3. 硬件嫌疑验证（软件侧只收证据，不下结论）
│   ├── 重启是否与负载峰值/外设动作/供电切换时刻相关
│   ├── 同批次多台是否同规律（个体焊点 vs 设计缺陷的粗判）
│   └── 带上证据清单 → hand-off fw-hil-testing（示波器/电源测量，真机定论）
└── 4. 修复与回归
    ├── 软件 → 修复 → 原路径复现验证；OTA 下发 → esp32-ota
    └── 硬件 → fw-hil-testing 出验收证据后再谈量产
```

## 3. 随机问题的证据加固手段

1. **coredump 常开**：随机崩溃的唯一事后证据（flash 目的地优先，UART 需人在场）。
2. **埋点日志**：关键阶段心跳打印，缩小"无声重启"的时间窗。
3. **记录启动原因**：每次启动把复位原因写入持久日志，积累分类样本。
4. **复现环境**：温度/负载/供电扰动逐项加减，找出触发因子——此步骤涉硬件测量即属 `fw-hil-testing`。

## 4. 常见误判

| 误判 | 实情 |
|---|---|
| "重启了 = 看门狗" | panic、掉电同样表现为重启；必须先取复位原因证据 |
| "coredump 里没有 = 没崩溃" | 掉电类崩溃来不及保存 coredump；没有记录本身是分类线索 |
| "偶发一次，忽略" | 随机问题不积累证据就永远定位不了；第一次就该开 coredump |
| "日志有电字样 = 供电问题" | 软件侧只能提嫌疑；定论必须实测（fw-hil-testing） |

## 缓解类观察项（仅作假设交付）

硬件嫌疑未实证前，可交付**时序错开类缓解观察项**（如“电机启动与敏感操作时序错开”“敏感写操作前加电压监测埋点”），措辞必须标注：`假设性缓解，因果未经 HIL 实证，验证路由 fw-hil-testing`。禁止写成结论性修复。

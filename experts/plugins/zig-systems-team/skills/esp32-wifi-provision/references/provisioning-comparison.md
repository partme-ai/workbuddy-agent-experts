# Provisioning Comparison：四种官方方式选型明细

来源：ESP-IDF 基线 §7（抓取官方 provisioning 文档，走读 2026-09-02，置信度高；未抓取处标注）。不自动更新。

## 1. 选型判据表

| 判据 | Unified Provisioning | SmartConfig | DPP | protocomm 直用 |
|---|---|---|---|---|
| 官方推荐度 | 推荐 | 列入索引，社区普遍视为 legacy | 列入索引 | 面向协议自研团队 |
| 手机端 | 官方 App（ESP BLE Provisioning / ESP SoftAP Provisioning） | 各厂商自实现，体验不一 | 需支持 DPP 的手机/入口 | 需自研 App |
| 传输 | SoftAP(+HTTP) 或 BLE(GATT) | 空口广播类机制（细节以官方文档为准） | 官方未抓取细节（运行时核验） | 自定义 |
| RAM 代价 | BLE 传输约 110KB（高置信）；SoftAP 另计 | 小（广播接收） | 未抓取 | 自定义 |
| 加密能力 | Security 0/1/2 完整方案 | 本身无统一安全方案 | DPP 自带安全机制（细节未抓取） | 取决于所选安全方案 |
| 可靠性 | 高（确认式协议，失败可回报） | 弱，依赖路由器/环境 | 未抓取 | 取决于实现 |
| 适用 | 量产新产品默认 | 存量兼容、演示 | 强互操作/扫码诉求 | 已有 App/协议团队 |

## 2. Unified Provisioning 内部再选型

1. **传输**：
   - BLE(GATT)：手机体验最顺（App 直连）；代价 ~110KB RAM（高置信）——小内存方案先量一下。
   - SoftAP(+HTTP)：无蓝牙芯片（如 S2）唯一 App 配网路径；用户需手动切 Wi-Fi 热点，体验略差。
2. **安全方案**：默认 Security 2（理由见 [security-scheme](security-scheme.md)）。
3. **指示与超时**：配网中必须有用户可感知指示；配网会话设上限，防设备卡在配网模式。

## 3. SmartConfig 使用纪律

- 仅当用户明确"存量产品/存量 App 兼容"时选它，并在方案文档标注可靠性弱。
- 不得在营销或验收口径里承诺"配网成功率"——它依赖空口广播，受环境影响大（基线未给量化数据，不编造）。

## 4. 状态机的"凭据失效重配"分支设计

- 触发源：用户改路由器密码、换路由器、认证反复失败。
- 设计要点：
  1. 连接失败次数设阈值，超阈值回到"配网中"并通知用户（App/指示灯）。
  2. 保留旧凭据直到新凭据**验证在线成功**再覆盖，避免"配一半两头空"。
  3. 提供"主动清凭据进配网模式"的物理入口（长按按键等），这是用户救砖的最后手段。
- NVS 持久化为"运行时核验"项：以上策略实现后必须真机断电重启验证。

## 5. 旧组件 `wifi_provisioning` → 现行组件 `network_provisioning`

- 基线确认：现行组件为 `network_provisioning`（registry/GitHub 示例）；旧组件 `wifi_provisioning` 文档仍在（v5.5 文档可见）。
- 迁移判据：新项目直接用现行组件；存量项目在升级 IDF 时评估迁移，协议兼容性差异以两份官方文档对照为准（未逐条抓取，运行时核验）。
- 准确包名/版本：以 `idf.py add-dependency` 在 registry 的运行时查询结果为准，写入 `idf_component.yml`，勿手抄记忆值。

# 工作流与检查点

## 1. 基线审计

读取目标仓库指令、规格、README、manifest、页面索引和代表性图片。记录文件路径、版本/日期、平台、设备、页面 ID、状态、是否被用户确认。不要把旧稿自动视为废弃，也不要把最新文件自动视为权威。

输出四类证据：源文件事实、用户裁决、带理由的推断，以及尚未执行的原生运行/暗色模式/可访问性等验证。

## 2. 语义差异审计

| 字段 | 检查内容 |
|---|---|
| 功能 | MVP 是否存在、是否同名不同义 |
| 入口 | 导航位置、首次启动、深链 |
| 状态 | 空、加载、运行、等待授权、完成、失败、暂停、恢复 |
| 事件 | 用户动作、工具调用、系统事件与状态转移 |
| 权限 | 触发时机、作用域、拒绝与重试 |
| 数据 | 同源文案、测试数据、持久化和清理 |
| 反馈 | 弹窗、抽屉、Toast、进度、错误恢复 |
| 后台 | 暂停、重启、恢复、通知和幂等 |

先列差异，再给裁决。说明为何属于共享合同或为何允许平台特化。

## 3. 页面矩阵

每个页面/关键状态一行：

```text
ID | 场景 | 触发 | 核心状态 | 可见结果 | 下一步 | Android Phone | Android Tablet | Apple Phone | Apple Tablet
```

稳定 ID 与展示名称分离。新增状态时先更新矩阵和规格。覆盖主流程、权限、错误恢复、删除确认、设置与后台恢复，不只覆盖 happy path。

## 4. 母版与设计语言

先选择或生成 Phone 主流程与 Tablet 主工作区母版。记录色彩角色与面积、空间层次、字阶与密度、圆角与间距、触控目标、图标来源，以及任务/权限/错误/恢复状态的视觉区分。

用户指出“深度和色彩品质不足”时，保留已确认的信息架构与交互，只重做材质、光影和色彩层级。

## 5. 成套生成

共享结构化场景输入：页面 ID、业务数据、状态、文案、插图引用和视觉令牌。先用小样确认设备与平台映射，再批量生成。沿用项目目录约定；若无约定可用候选树：

```text
design-ui-next/
  shared/
  android/phone/
  android/tablet/
  apple/phone/
  apple/tablet/
  manifest.json
```

## 6. 验证与提升

- 页面 ID 集合与矩阵一致。
- 四端文件命名和覆盖可对应。
- 图片可解码、尺寸正确、无裁切/溢出/空白。
- 文案、状态、插图与同源输入一致。
- 代表图通过层级、色彩、密度、平台习惯和 Tablet 重排审查。
- README、规格链接和 manifest 路径可解析。

报告用 `PASS / FAIL / NOT VERIFIED / NEEDS DECISION`。候选目录通过用户审核后才计划提升；删除旧树或历史稿必须另获授权。
